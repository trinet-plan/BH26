# BH26 ExpertBoard (Pan-Asian Variant Review Network) — Participant Briefing

**version: v3**

---

## 1. About this project

ExpertBoard is an effort to semi-automate variant interpretation (ACMG/AMP classification) for hereditary diseases, where AI assists in gathering Evidence and experts make the final decision. We are carrying forward the results from MedHackathon Asia 2026 (Singapore) and developing them further at this BH26.

The results from BH26 are planned to be submitted as a Perspective to the special issue *"Artificial Intelligence Applications in Rare Disease Research and Care"* in the Rare Disease and Orphan Drugs Journal.

### Core principles

1. The system prepares candidate Evidence. Experts judge its value.
2. Evidence must be reproducible and traceable.
3. LLMs do not directly finalize the pathogenicity classification.
4. LLMs may actively support the discovery, structuring, and gap analysis of Evidence.
5. Ontology/DB identifiers (e.g., HPO IDs) are established based on authoritative sources, not freely generated by an LLM.
6. The accuracy of Evidence depends on the diversity of the population frequency data referenced. Data centered on European/American populations alone can produce incorrect Evidence (frequency-based evidence) for Asian patients.

### The one thing we most want to convey

This project's claim is not that we "collected Pan-Asian frequency data." The main point is that **we are building, in Asia, the semi-automated mechanism for gathering Evidence itself**. The demonstration using Pan-Asian frequency data is positioned as one compelling example supporting that claim.

## 2. What we are building

### 2-1. Overall flow

```
Case (multiple candidate Variants, with ground-truth data)
    ↓
Evidence Preparation (modules per criterion)
    ↓
Generated Evidence (Criterion + Strength + Source)
    ↓
Classification module (computed via deterministic rules)
    ↓
Comparison tool (matched against ground-truth data)
    ↓
Concordance rate / discrepancy report
```

Rather than the final classification, we treat the **Evidence Record** (a record of candidate evidence) as the central data. Each tool/LLM generates "Candidate Evidence" rather than a final judgment. This time, **we will not build a screen for a human to Accept/Reject/Modify on the spot**. Instead, results are automatically checked against pre-prepared ground-truth data.

### 2-2. Evidence Record (minimal schema, draft)

- **Variant**: which variant this evidence pertains to
- **Candidate Criterion**: e.g., PM2
- **Candidate Strength**: e.g., Supporting / Moderate / Strong / Very Strong
- **Evidence source**: which tool/data it came from, plus the actual value/rationale (e.g., "gnomAD AF=0.00008," "REVEL=0.97," "ClinVar VCV000012345, reviewed_by_expert_panel")

This is a draft. The whole team will review and finalize it on-site on Day 1.

### 2-3. Evidence Preparation (5-layer structure)

The following is not a fixed classification but a provisional implementation scheme as of BH26. Since "how far can this actually be automated" is not something we know without trying, verifying this boundary between Automated/Semi-automated/Manual is itself part of this task.

| Layer | Content | Corresponding ACMG codes | Implementation |
|---|---|---|---|
| 0. Triage | Narrowing thousands of variants down to candidates | — | `vep_parser.py` (to be extended) |
| 1. Automated Evidence | Mechanically judged from structured data | PVS1, PS1, PM1, PM2, PM4, PM5, PP2, PP3, PP5, BA1, BS1, BP1, BP3, BP4, BP6, BP7 | Existing deterministic tools such as InterVar/AutoPVS1 |
| 2. Semi-automated Evidence | Judgment using phenotype | PP4 | PubCaseFinder (input is free-text clinical narrative) |
| 3. Evidence Gap / Manual Review Required | Flags points that cannot be judged with current data | PS2, PS3, PS4, PM3, PM6, PP1, BS2, BS3, BS4, BP2, BP5 | Rules + LLM (Evidence Gap Analysis) |
| 4. Documentation | Natural-language summary of evidence and conclusions | — | Local LLM |

**Basis for Strength**: Not decided arbitrarily — we follow existing calibrated criteria (PVS1 per the AutoPVS1 decision tree; PM2 downgraded to Supporting per ClinGen SVI recommendation; PP3/BP4 per Pejaver et al. 2022's calibrated thresholds; others per ACMG/AMP 2015 defaults).

**Boundary cases**: PM3 (confirming trans configuration) and BS2 (observation in healthy individuals) could potentially be automated/semi-automated with trio VCF data or population health databases, but are currently placed in the Evidence Gap layer given available data sources. These are points we want to confirm on-site.

### 2-4. Role of the LLM: Evidence Copilot

The LLM does not make the final call. It is an "umbrella" covering the following four functions.

| Function | Description |
|---|---|
| Natural-language summary | Summarizes already-generated Evidence in natural language. Does not generate new Evidence |
| Evidence Gap Analysis | Surfaces "the gap between current Evidence and what is needed to decide." Ideally also suggests what to do next |
| Draft classification and evaluation of the computed result | Two stages: ① a blind draft classification based on Evidence alone → ② an evaluative comment after being shown the Classification module's computed result |
| HPO extraction | Extracts HPO terms from free-text clinical narrative (needed as input for PP4) |

## 3. Deterministic vs. LLM comparison experiments (this cycle's Priority, three pillars)

To test "how far AI (LLMs) can support Evidence," we will prioritize the following three, each comparing a deterministic method/tool against an LLM given the same input.

1. **PVS1**: AutoPVS1's decision tree vs. LLM. AutoPVS1 has clearly documented logic, so we can measure whether the LLM can implicitly reproduce it.
2. **Evidence Gap Analysis**: a simple null check vs. LLM free-text output. We test whether the LLM's output is genuinely valuable, not just a paraphrase of the null check.
3. **HPO Grounding**: naive LLM-based HPO extraction (Critical path) vs. extraction grounded via TogoMCP ontology lookup (if time permits).

**Bonus**: We will also record, as a byproduct once the other modules are complete, the result of feeding the raw VCF and clinical narrative directly to an LLM and letting it produce everything from Evidence organization through Classification in one pass. However, given the scale of the Demo Cases, the statistical persuasiveness is limited, so this will be treated as a reference result only.

## 4. Demo Cases (already built from real cases)

We have prepared four cases. All are based on real case reports/real databases, and ground-truth data has also been prepared.

| Case | Disease / Source | Pattern |
|---|---|---|
| **1** | HCM, Han et al. 2026 (real case, Chinese patient). DOI: [10.3389/fcvm.2026.1841777](https://doi.org/10.3389/fcvm.2026.1841777) | Phenotype mismatch: MYBPC3 (the true causal candidate) and KCNJ5 (an incidental finding, a gene unrelated to HCM) are found together |
| **2** | Lethal neonatal HCM, Wang et al. 2025 (real case). DOI: [10.3389/fcvm.2025.1726463](https://doi.org/10.3389/fcvm.2025.1726463) | Compound heterozygous: both variants are required as the cause (not a "narrow down to one" pattern) |
| **3** | HCM (variants/frequencies are real, patient narrative is constructed). MYBPC3-side source DOI: [10.1161/CIRCGEN.122.003736](https://doi.org/10.1161/CIRCGEN.122.003736) (MYH7 side is ClinVar VCV000014104, no DOI) | Pan-Asian: MYH7 (Pathogenic, formally verified by ClinGen) and MYBPC3 p.Glu334Lys (a real example where frequency data from the Singapore SG10K cohort changed the classification) |
| **4** | ARVC, Human Genome Variation journal (real case, Japanese patient). DOI: [10.1038/s41439-022-00206-9](https://doi.org/10.1038/s41439-022-00206-9) | Pan-Asian: DSG2 p.Phe531Cys, up to ~14x higher frequency in the Japanese population (ToMMo) than in gnomAD overall |

Each case has also been independently annotated with AlphaMissense and AlphaGenome (missense pathogenicity prediction and splicing-impact prediction, respectively).

**The confidence of the ground-truth data has a tier structure**:

- **Tier A**: Formally verified per-criterion by a ClinGen Expert Panel (only MYH7 in Case 3)
- **Tier B**: The paper's authors explicitly state the rationale
- **Tier C**: A real, existing disagreement is itself the "answer" (the fact that opinion is split is itself the ground truth)

Rather than hiding this, we reflect it in the comparison tool's output as well. This is itself an embodiment of the principle of "preserving the provenance and confidence of evidence."

**The overall passing bar is the concordance check for Case 1.** Cases 2-4 will be tackled as time and effort allow.

## 5. What we are NOT building this time

The following are not included in the scope of this BH26. The reasons: these specifications are hard to finalize, and any provisional decision risks not matching the on-site situation; also, participants' interest is strongly weighted toward the Evidence Preparation side.

- A review screen where a human performs Accept/Reject/Modify
- A role-based Board approval mechanism
- Keycloak/RBAC

Instead, automatic matching of results against ground-truth data via the comparison tool serves as this cycle's "verification."

## 6. Module division and interfaces

Since Keycloak/RBAC/the review screen are out of scope, the team will divide work as **multiple independent modules connected via the common Evidence Record schema**.

| Module | Input | Output |
|---|---|---|
| Layer 0: Triage | VCF + annotation | Narrowed-down candidate variant list |
| Layers 1-3: Evidence generation | Candidate variant + annotation | Set of Evidence Records |
| Evidence Gap Analysis | Set of Evidence Records | Report of missing Evidence |
| Classification module | Set of Evidence Records | Per-variant classification |
| Comparison tool | Evidence Records, Classification, ground-truth data | Concordance / discrepancy report |

**Operating rules**:

1. Freeze the Evidence Record schema at the start of Day 1 PM; everyone implements according to it.
2. Each module can be implemented and tested independently (unit-testable with dummy data; no need to wait for other modules to finish).
3. Bring the integration checkpoint forward, well before the final day (targeting 9/17).
